# SLSA compliance assessment

Honest assessment of the caddy-waf build pipeline against
[SLSA v1.0](https://slsa.dev/spec/v1.0/) supply-chain levels, based only on
what the repository actually implements.

## Pipeline at a glance

| Stage | Implementation | Evidence |
|-------|----------------|----------|
| Source | Tagged releases (`v*`) trigger the release pipeline; PRs only run validation | .github/workflows/docker-build-scan-sign.yml:5-7,98-99 |
| Build | Multi-arch (amd64+arm64) build on GitHub-hosted runner (`ubuntu-latest`) | .github/workflows/docker-build-scan-sign.yml:22,98-109 |
| Gate | Trivy scan fails the build on CRITICAL/HIGH (unfixed ignored); amd64 scan before push | .github/workflows/docker-build-scan-sign.yml:50-88 |
| Sign | Cosign keyless (OIDC) signature of the image by digest | .github/workflows/docker-build-scan-sign.yml:120-131 |
| SBOM | CycloneDX SBOM generated and attached as Cosign attestation | .github/workflows/docker-build-scan-sign.yml:111-118,133-141 |
| Provenance | SLSA provenance via GitHub's `attest-build-provenance` action, pushed to the registry | .github/workflows/docker-build-scan-sign.yml:143-149 |

## Level-by-level assessment (SLSA v1.0)

### Level 1 — baseline

| Requirement | Status | Notes |
|-------------|--------|-------|
| Version-controlled source | ✅ | Git; releases are `v*` tags |
| Scripted build | ✅ | Single Docker build via CI workflow |
| Provenance available to consumers | ✅ | Provenance attestation published alongside the image (.github/workflows/docker-build-scan-sign.yml:143-149) |

**Level 1: met.**

### Level 2 — hosted build + signed provenance

| Requirement | Status | Notes |
|-------------|--------|-------|
| Hosted build platform | ✅ | GitHub-hosted ephemeral runner — the builder is not the maintainer's machine |
| Provenance authenticated (signed, identifies builder) | ✅ | Generated by GitHub's SLSA provenance generator and signed with the runner's OIDC identity |
| Source provenance | ✅ | Build tied to a `v*` git tag |

**Level 2: met.**

### Level 3 — hardened build + non-falsifiable provenance

| Requirement | Status | Notes |
|-------------|--------|-------|
| Provenance generated by the build platform itself (non-falsifiable) | ✅ (partial) | `attest-build-provenance` is the trusted builder generating the attestation |
| Hardened build platform | ⚠️ | GitHub-hosted runners are isolated/ephemeral, but the build is **not hermetic**: it downloads dependencies at build time (Alpine `apk upgrade` — Dockerfile:38, `go mod` fetches, OWASP CRS tarball — Dockerfile:50) |
| No source-modifying build steps | ⚠️ | Build step runs unverified third-party fetch; pins mitigate (SHA256 checksums — Dockerfile:43,52,59; pinned versions — Dockerfile:48) but do not make the build hermetic |
| Reproducible builds | ❌ | No reproducibility claim or digest comparison across builds |

**Level 3: not met** (provenance artifact is L3-class, the build itself is not).

## Common threats and mitigations

| Threat | Exposure | Mitigation in place |
|--------|----------|---------------------|
| Maintainer account compromise pushes a malicious tag | High (single maintainer, no branch protection) | Keyless Cosign + OIDC provenance tie the artifact to the GitHub identity; no signing secrets in CI (`id-token: write` only, .github/workflows/docker-build-scan-sign.yml:13-18); persistent credentials disabled (.github/workflows/docker-build-scan-sign.yml:27) |
| Dependency substitution (compromised apk/go module/CRS) | Medium | SHA256 verification of CRS tarball and `coraza.conf` at build time (Dockerfile:50-59); pinned apk versions (Dockerfile:48); Actions pinned by SHA |
| Build tampering on the runner | Low | Ephemeral GitHub-hosted runner; provenance signed by the runner's OIDC token |
| Provenance forgery | Low | Provenance generated by GitHub's SLSA generator, not by maintainer scripts |
| Image tampering in the registry | Low | Signature + attestation by digest, verified with `cosign verify` before pull (README.md:276-287) |

## Remaining gaps to L3+

1. **Hermetic builds** — vendor/pin all build inputs (Go module cache, apk
   versions, CRS tarball) so the build needs no network.
2. **Reproducible builds** — build twice, compare digests; publish the digest
   comparison in CI. Precondition: hermetic inputs.
3. **Two-person review** — single maintainer today; any second reviewer would
   enable branch protection and release approval.
4. **Branch protection on `main`** — requires a second account, currently N/A
   (single maintainer); revisit as soon as the project gains collaborators.

## Current level

**L2, with a partial-L3 provenance artifact.** The pipeline produces
non-falsifiable, signed provenance from GitHub's trusted builder (an L3
property), but the build itself is not hermetic or reproducible and releases
have no two-person review — so the honest overall claim is **SLSA Level 2**,
with a clear path to L3 via the gap list above. Small project, no
overclaiming.
